# 后端 Bug 排查标准模板

## 核心结论

后端排查 bug 最实用的标准模板，不是“想到哪查到哪”，而是固定成一套 **问题登记 → 复现确认 → 链路定位 → 根因假设 → 修复验证 → 复盘沉淀** 的闭环。
对于程序员来说，真正高效的不是经验多，而是每次都按同一套模板把问题压缩到：**哪条请求、哪段代码、哪份数据、哪个环境、哪项变更**。

---

## 需求分析

### 你这次要的是什么
你要的是一个**后端程序员可直接套用的 bug 排查标准模板**，而不是理论解释。

### 最终要解决什么
解决三个核心问题：
* 接到 bug 后，第一步做什么
* 如何避免盲查、乱改
* 如何形成可复用的排查记录

### 使用场景
适用于典型后端问题：
* 接口报错
* 返回数据异常
* 状态流转错误
* 数据库写入失败
* 并发问题
* 超时/性能问题
* 偶发性线上故障
* 配置/环境差异问题

---

## 问题界定

### 约束
后端查 bug 常见约束包括：
* 线上不能随便改
* 日志不完整
* 本地难复现
* 数据涉及真实业务，不能乱动
* 问题影响范围大，必须先止血
* 时间紧，先恢复业务再谈彻底治理

---

### 5. 链路定位

#### 分层检查结果
按下面顺序逐层打勾：
1. **接入层**: 网关是否收到请求 / 鉴权是否通过 / 路由是否正确
2. **Controller 层**: 是否进入接口方法 / 参数是否成功绑定 / 参数校验是否通过
3. **Service 层**: 是否进入目标业务逻辑 / 关键分支是否命中 / 关键变量值是否符合预期
4. **DAO / DB 层**: SQL 是否执行 / SQL 结果是否正确 / 是否有锁等待、超时、唯一键冲突
5. **缓存 / MQ / 第三方**: 是否调用成功 / 超时还是业务失败 / 返回值是否异常 / 是否有重试/重复消费
6. **返回层**: 返回封装是否正确 / 是否被统一异常处理器改写 / 是否被网关/中间件拦截

---

### 6. 根因假设

#### 6.1 假设列表
**模板：**
* **假设A**：描述、支撑证据、反证点、验证方法
* **假设B**：描述、支撑证据、反证点、验证方法

#### 6.2 根因确认
最终要写清楚：
* **直接原因**：系统直接报错点 (如 NullPointerException)
* **深层原因**：为什么出现该报错 (如 上游字段为空未校验)
* **根本约束**：为什么系统长期容易出这类问题 (如 缺参数校验、缺回归测试)

| 方案 | 动作 | 收益 | 风险 | 难度 | 适用性 |

| 方案C | 增加兜底默认值 | 降低报错率 | 可能掩盖数据问题 | 低 | 中 |

#### 7.2 主方案
* 选用方案：
* 原因：

* 灰度/回滚：是否需灰度 / 是否需回滚预案

---

### 8. 验证路径

#### 8.1 必测清单
建议固定测这几类：
* 正常参数 / 空值参数 / 极限参数
* 重复请求 / 并发请求
* 权限边界 / 脏数据场景 / 第三方失败场景

#### 8.2 观察指标
* 接口成功率
* 500 错误数
* 业务失败率
* 响应时间
* 数据写入成功率
* 告警数量

---

## 风险提醒

后端排查 bug 最常见的失误有五个：
1. 把异常点当根因
2. 把偶发问题当必现问题
3. 把线上数据问题当代码问题
4. 把配置问题当逻辑问题
5. 修完不补自动化测试和监控
