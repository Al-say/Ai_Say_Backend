## 🧠 思维模型升级清单

### 1. **系统论 → 识别关键约束**

**问题识别**:
- AI 调用延迟 5-30 秒 → HTTP 超时（约束）
- DeepSeek 返回格式不稳定 → 解析失败（脆弱点）

**解决方案**:
- 异步架构 → 解除时间约束
- 多层解析 + 降级策略 → 提高鲁棒性

### 2. **终局思维 → 先定义契约**

**传统做法**:
```
写 Controller → 写 Service → 前后端联调 → 反复修改
```

**终局思维**:
```
定义 DTO（数据契约） → 前后端并行开发 → 集成一次成功
```

**关键洞察**: `EvaluationRequest` 和 `AsyncEvaluationResponse` 就是"接口的接口"，比代码更重要。

### 3. **工程卓越 → 安全无小事**

**脆弱点**:
```yaml
deepseek.api.key: sk-1234567890abcdef  # ❌ 泄露风险
```

**零信任原则**:
```yaml
deepseek.api.key: ${DEEPSEEK_API_KEY:dummy-key}  # ✅ 安全
```

**扩展思考**: 这不仅是技术问题，更是**职业习惯**的养成。

## 📊 架构决策记录（ADR）

### ADR-001: 采用异步任务模式

**上下文**: AI 评估耗时 5-30 秒，超过典型 HTTP 超时阈值。

**决策**: 使用 TaskID + 轮询模式，而非同步阻塞。

**理由**:
1. **用户体验**: 立即响应（< 100ms）vs 长时间等待
2. **资源效率**: 释放 Tomcat 线程 vs 线程阻塞
3. **可扩展性**: 支持并发 100+ 任务

**权衡**:
- 增加了客户端轮询复杂度
- 需要管理任务状态存储

**替代方案**:
- SSE（Server-Sent Events）: 实时推送，但客户端支持有限
- WebSocket: 双向通信，但对于单向推送过重

---

### ADR-002: 使用环境变量管理敏感配置

**上下文**: API Keys、数据库密码等敏感信息不能提交到 Git。

**决策**: 所有敏感配置使用 `${ENV_VAR:default}` 模式。

**理由**:
1. **安全性**: 代码与密钥分离
2. **灵活性**: 开发/测试/生产环境切换无需修改代码
3. **合规性**: 符合安全审计要求

**实施**:
```yaml
deepseek.api.key: ${DEEPSEEK_API_KEY:dummy-key}
```

**最佳实践**:
- 提供 `.env.example` 模板
- `.gitignore` 排除 `.env` 文件
- CI/CD 通过环境变量注入真实值

## 🔍 代码审视：为什么这样设计？

### 案例 1: `AsyncEvaluationResponse` 的工厂方法

```java
public static AsyncEvaluationResponse pending(String taskId) {
    return AsyncEvaluationResponse.builder()
            .taskId(taskId)
            .status(TaskStatus.PENDING)
            .progress(0)
            .estimatedSecondsRemaining(15)
            .build();
}
```

**设计意图**:
1. **语义化**: `pending(taskId)` 比 `new AsyncEvaluationResponse(...)` 更易读
2. **封装变化**: 初始化逻辑集中，未来修改只改一处
3. **类型安全**: 避免构造参数顺序错误

---

### 案例 2: 线程池配置的精妙之处

```java
executor.setCorePoolSize(5);       // 核心线程
executor.setMaxPoolSize(20);       // 最大线程
executor.setQueueCapacity(100);    // 队列容量
```

**背后的思考**:

| 参数 | 值 | 原因 |
|-----|---|------|
| 核心线程 | 5 | AI 调用是 IO 密集型，不需要太多常驻线程 |
| 最大线程 | 20 | 高峰期可扩展，但避免上下文切换开销 |
| 队列容量 | 100 | 平衡内存占用和缓冲能力 |

**计算逻辑**:
```
最大并发 = 核心线程 + (队列容量 > 0 ? 队列 : 最大线程-核心线程)
         = 5 + 100 = 105 个任务
```

**拒绝策略**: `CallerRunsPolicy` → 降级到主线程执行，而非抛异常。
